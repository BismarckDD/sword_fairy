# 游戏数据解析与扩展方案

核对日期：2026-10-16。依据当前 C 代码和本地资源；尚未进行修改后游戏运行验证。本方案不改变现有游戏资源或存档。

## 已解析成果

运行 `tools/export-game-database.ps1` 可在 `runtime/analysis/` 生成 `database.json` 与 `database-report.md`，包含 16 个角色、64 个敌人、64 个技能、64 个物品，共 208 条记录。报告列出技能动画文件存在性，JSON 保留所有原始字节及未命名字段。运行目录被 Git 忽略，解析结果不应作为公共源码提交。

所有 ID 都是从 0 开始的记录索引；文件偏移为 ID × 记录长度。整数为小端 WORD，但经验、数量等字段有无符号语义，不能统一按有符号数修改。名称按 GB936 解码，原字体使用 GB2312 区位索引，GBK 扩展字符未必可显示。导出工具读取名称开头最多 12 字节；不据此断言技能全部前 16 字节均可用于名称。

## 字段依据

### MAN.DAT：每条 68 字节

| 偏移 | 含义 |
|---|---|
| 00–0B | 角色名称，12 字节含 NUL |
| 0C / 0E | 菜单头像编号 / 世界人物资源编号（由调用用途判断） |
| 10 / 12 | 当前生命 / 内力 |
| 14 / 16 | 最大生命 / 内力 |
| 18 / 1A | 基础攻击 / 防御 |
| 1E | 当前等级内积累经验，无符号 WORD |
| 20 | 投掷物动作动画编号；新游戏还会覆盖前五个角色此字段 |
| 22 | 等级 |
| 24 | 状态：1 醉酒，2 中毒 |
| 26 | THING.DAT 装备 ID |
| 28 | 普攻动画编号 |
| 2A / 30 | 普攻 / 另一动作音效资源编号 |
| 2E / 32 | 死亡 / 低生命姿态图编号 |
| 34–43 | 16 个技能槽，每槽一个有符号字节；FF 为空 |

1C、2C 等未确认字段保持原样。显示与计算的攻击、防御会叠加装备的加成。虽然有 16 条角色记录，升级和部分角色菜单仅接受 ID 0–4，不应把所有记录视作可直接加入的主角。

### ENEMY.DAT：每条 30 字节

名称位于记录开头；0E 生命、10 攻击、12 防御、14 普攻动画编号、18 技能 ID、1C 经验奖励。其余字段保留原始值。战斗开始把整条记录复制到 DS:6606；因此战斗中的 DS:6614 为生命，DS:661E 为技能 ID。敌人普攻与技能分支由当前回合逻辑随机选择，不是按记录配置技能列表。

### SKILL.DAT：每条 28 字节

| 偏移 | 含义 |
|---|---|
| 00 起 | 名称字符串，遇 NUL 结束；建议兼容修改限制在 11 个编码字节内 |
| 10 | 技能基础伤害，按有符号 WORD 使用 |
| 14 | 内力消耗，比较时按有符号 WORD 使用 |
| 18 | 动画编号 |
| 1A | 音效编号，负值通常用于无资源 |

0C、0E、12、16 等字段未证明有扩展用途，不应用来偷偷存储新功能。当前技能分支直接取基础伤害，不减敌方防御；角色两人的伤害相加后再进行浮动处理。不能把本表理解为带目标、范围、治疗、增益等行为的通用技能系统。

### THING.DAT：每条 28 字节，装备与物品共表

0E 在补给中表示恢复生命，在投掷分支表示伤害；10 增加生命上限；12 恢复内力；14 增加内力上限；16 攻击加成或永久增加攻击；18 防御加成或永久增加防御。其他字段保留原值。物品的类别不从一个类型字段读取，而由 ID 判断：

| ID | 当前分支 |
|---|---|
| 0 | 无物品，背包空位 |
| 1–11 | 装备，角色只有一个装备槽 |
| 12–37 | 特殊处理函数，包含剧情用途，需逐项审计 |
| 38–58 | 补给，更新上述六种属性 |
| 59–63 | 战斗投掷分支 |

图标从 `fight/thing.inf` 读取，ID × 3120 定位，每项 60×52 字节像素。扩展物品时必须处理对应图标。商店价格及特殊道具逻辑还需追踪相关调用，不能把未知 WORD 直接当成价格。

## 技能如何对应动画

调用链：`events_battle_turn.c` 取技能 +18 → `jx_battle_cache_actor_animation`（events_battle_drawing.c）拼文件名 → `jx_battle_cache_animation` 解码和裁剪 → `jx_battle_draw_animation_frame` 逐帧绘制。

- 主角与队友：`fight/frien` + 三位十进制 `(动画编号 - 100)` + `.anm`。
- 敌人：`fight/enemy` + 三位十进制 `动画编号` + `.anm`。
- 衡山有雪，技能 ID 9，动画 101 → `fight/frien001.anm`，威力 20，消耗 5，音效 66。
- 风雷九州，技能 ID 19，动画 107 → `fight/frien007.anm`，威力 800，消耗 250，音效 69。
- 饿虎扑食，技能 ID 0，动画 2 → `fight/enemy002.anm`。

动画不是按技能名称搜索。现有资源通常含角色自身动作，复用动画可能连施法者外观一起复用。主角动画裁剪原帧 (14,27) 起 220×148，敌人 (1,1) 起 220×148；透明绘制色为 255。原帧布局按 320 像素行宽解码，生成新动画应匹配当前 ANM 格式和调色板。

每一方预留 16 个 EMS 页，每帧占两页；回合固定绘制帧 0–7。所以兼容新增动画应制作恰好 8 帧。超过 8 帧可能覆盖相邻缓存，少于 8 帧可能读旧帧。负动画编号仅提前返回，不会主动清空缓存，不能拿 -1 当作可靠的“无动画”行为。

技能 +1A 音效目前仅在第一名我方角色施法时加载到缓存槽 10，回合也只按第一名角色的命令选择播放槽 10 或普攻槽 6。第二名我方角色和敌人的技能不能仅修改本字段就获得独立技能音效，需要同步调整回合播放逻辑。

## 方案 A：保持原布局，适合先做少量内容

1. 增加可读配置层：以 UTF-8 JSON 编辑，独立构建工具校验并生成本地 DAT。固定原 ID，不重排；未知字节保留，输出文件先放独立目录，经验证后应用。工具需校验表长、字段范围、名字编码长度、引用 ID、动画文件、8 帧约束和图标数量。
2. 改名：技能、物品、装备名称直接修改各自记录开头；保守限制为 11 个 GB2312 编码字节加 NUL，通常最多五个汉字；清零名称保留区，不能移动后面的数值。较长名称需要一并改布局、字符串缓冲区和菜单宽度。修改技能名和物品名通常无需改存档；角色名字在存档角色表内，旧存档会覆盖基础角色名字。
3. 新技能：62、63 目前名为“武功02/武功03”，动画与音效均 -1，可作为候选槽，但必须搜索剧情引用、角色初始技能和敌人技能，证明无用途后再占用。设置威力、消耗、动画和音效，再通过初始技能、剧情授予或升级规则获得。不能只添加 DAT 第 65 条，加载器只读 64 条。
4. 新装备与物品：当前 64 条均有记录，不能默认存在空槽。可以有意识替换已有内容；要把 12–37 的某项改成新装备/补给，必须改用明确类型元数据，并移除该 ID 的特殊用途冲突。新增装备仍共用一个装备槽；增加头盔、护甲等槽位属于存档与属性计算改造。
5. 资源复用优先：先使用已存在的对应施放方动画和图标，验证玩法后再制作新资源。补充商店、拾取、剧情奖励等获取入口；定义条目本身不会自动出现在游戏里。

## 升级学习技能

当前 `jx_actor_level_up`（events_actor_restore.c）只升级、增加属性和恢复生命内力；剧情通过 `jx_actor_skill_grant` 单独授予技能。建议新增显式规则配置，例如：

```json
{
  "version": 1,
  "learn_rules": [
    { "actor_id": 0, "level": 5, "skill_id": 19 },
    { "actor_id": 1, "level": 10, "skill_id": 20 }
  ]
}
```

以上仅为格式例子，不代表平衡推荐。接入点放在统一的 `jx_actor_level_up` 完成等级增长后，覆盖战斗连续升级和剧情直接升级。若保留独立的 `jx_level_up_core` 路径，也应共享同一规则评估，避免两套行为分叉。

按旧等级 < 学习等级 <= 新等级触发；授予前扫描全部 16 槽排重，再找空槽。现有授予函数遇空位即返回，空位之后有同 ID 时会重复，因此不能直接依赖其去重行为。满槽时给出明确提示，选择遗忘或记录待学习，不能静默丢失，也不能把技能字节截断。旧存档加载时是否补授 level <= 当前等级的技能应做成明确迁移选项；无条件补授会把主动遗忘的技能重新加回。

初始配置已包含较多技能。例如独孤剑有 9、10、11、12、13、61；若希望这些技能改为按等级学习，还需从初始表移除，并设计旧存档迁移。保留剧情专属技能的授予条件；技能 30“天魔解体”在敌人 15 的战斗中有显式剧情特判，不能随意重用其 ID 或按普通伤害技能处理。

## 方案 B：真正扩容，适合持续增加内容

不要扩大固定 DS 数组后直接挤占后面的内存。敌人表紧邻技能表，物品表也紧邻游戏全局状态。应建立独立的本机数据容器和访问接口，逐步替换所有 `固定地址 + ID × 长度` 调用：

- 统一 actor/skill/item/enemy 查询接口，配置独立保存名称、类型、属性、动画路径、音效和行为。
- 原 ID 0–63 保留；新增 ID 从 64 起，旧剧情仍按原 ID 工作。菜单、奖励、商店、装备计算、敌人施法都必须走新接口，不能只改加载函数。
- 技能槽当前为有符号字节，128 及以上会当作空槽；需改为足够宽的 ID 和动态技能列表。背包 64 格与物品表 64 条是不同限制，分别处理。
- 动画改为显式路径、帧数、裁剪与调色板元数据；重做按帧分配缓存和回合调度，消除固定八帧及文件名减 100 规则。
- 物品按类型调度；装备槽、使用目标、消耗规则和特殊效果独立描述。新治疗、增益、群攻技能需要新增行为实现，而非填未知字段。
- 设计带版本的新存档或伴随扩展存档，保存扩展背包、装备、技能和待学习状态；提供旧 SAVE 导入，禁止新状态无提示截断成旧格式。

推荐顺序：可读配置与校验 → 少量兼容技能和升级规则 → 类型化物品 → 数据访问接口迁移 → 扩容与新存档 → 新动画/效果系统。

## 验证要求

导入导出保持未修改文件逐字节一致；非法 ID、超长名称和缺失资源应被拒绝。验证单人/双人战斗技能、敌人技能、内力不足、装备交换与背包、连续升级、重复规则、技能满槽、剧情直接升级、保存后读回及旧档迁移。动画须实际检查八帧、裁剪、透明色和双方位置，音效须单独听看确认。现阶段仅完成读取和静态对应关系检查，尚未实施上述玩法变更。
